# io_protocol

Two things that are usually separate projects, kept together because one is
built on the other: **a storage engine** whose updates are field-granular over
an append-only log, and **a secure UDP transport** on `io_uring`. Replication is
the seam - it is the only component that touches both.

| | what it is | depends on | platforms |
|---|---|---|---|
| `storage/` | the field-granular engine | nothing but libstdc++ and POSIX | Linux, Android tested; macOS/iOS unverified |
| `embedded/` | platform shims and the epoll transport | `libsodium` for the transport | as above |
| `replication/` | WAL shipping and snapshot bootstrap | a transport | Linux, Android tested |
| `net/` | the protocol, levels 1-7, plus the io_uring transport | `libsodium`; `liburing` for that one transport | Linux |
| `runtime/` | fibers and a multi-thread queue | POSIX `ucontext` | Linux |

**Support is not uniform, and the table above is the honest version.** The
protocol itself is portable - the handshake, reassembly, AEAD, the replay
window, anti-DoS and reliability never mention io_uring - and picks its
transport as a template parameter: `net/uring_io.hpp` where io_uring is
available, `embedded/epoll_udp.hpp` where it is not. On Android that is not a
matter of kernel age: **io_uring is blocked for apps by seccomp**, so epoll is
the permanent answer there rather than a fallback.

What stays Linux-only is `net/uring_io.hpp` itself and `runtime/fiber.hpp`,
the latter because `ucontext` left POSIX in 2008 and is absent from the iOS SDK.
The Darwin paths in `embedded/platform.hpp` are **written and reviewed but not
run** - see below.

# The storage engine

One append-only log over `mmap`, indexed per **field** rather than per record.
Nothing is ever patched in place, so changing eight bytes of a kilobyte record
writes eight bytes - where a B+tree or a heap table rewrites the row.

Full specification: **[`storage/FIELD_STORAGE.md`](storage/FIELD_STORAGE.md)**.

## What that buys, measured

All three engines at an **identical 10,000-record crash window**, on the same
1-vCPU VPS, one process per cell, page cache dropped between them. Detail and
method in [§8b](storage/FIELD_STORAGE.md).

| 1 GB on 960 MB of RAM, 300,000 operations | this engine | LMDB | ObjectBox |
|---|---|---|---|
| random update | **543,070** | 2,308 | 1,758 |
| major faults over 300,000 updates | **164** | 180,305 | 229,770 |
| iowait during the update phase | **0.01 s** | 90.74 s | 116.59 s |
| random read | **5,461** | 4,131 | 2,753 |
| fill | 249,105 | **283,158** | 178,002 |
| on disk per 1 GB of data | **1.05 GB** | 1.34 GB | 2.11 GB |

The update column is the design, and the two rows under it say why: an append
touches no page of the record, so there is nothing to fault on and nothing to
wait for. Both in-place designs stall on the device.

**Reads are the cost, and only while the data fits.** In RAM, `storage.hpp`'s
contiguous record is 4x faster to read, because a read there is a pointer and
here it is a gather. Out of RAM the two converge, since every read is a fault
either way.

One caveat the spec spells out: an out-of-RAM *update* rate for this engine
depends on how much of the set a run sweeps, because it is the only engine here
that is not fault-bound anyway. Read it as a range - three runs of the cell
above gave 377,015, 435,691 and 543,070 - not as a figure.

One writer per instance, which is the unit of scale rather than a ceiling -
sixteen independent instances on this desktop reach **125.8M updates/sec**, and
six of them 130.8M at 87% efficiency (`bench/shard_scaling.cpp`). LMDB and
ObjectBox are single-writer too, so more threads do not help them.

## Using it

The engine is header-only and needs nothing but the standard library and POSIX.
Either take one file:

```cpp
#include "field_storage.hpp"      // dist/field_storage.hpp - copy it and go
```

or three from the tree, keeping their relative layout:

```
storage/storage.hpp
storage/field_storage.hpp
embedded/platform.hpp
```

`dist/field_storage.hpp` is generated by `tools/amalgamate.py` and cannot go
stale: `ctest` regenerates it and diffs, and a separate case compiles a
translation unit that includes it and nothing else.

```cpp
struct account {
    static constexpr storage::tag_t tag = 1;
    uint64_t balance, opened_ms;
    char     name[64];
};

using spec = storage::field_spec<
    "data.log", 8ull << 30,      // the log
    "data.idx", 1'000'000,       // one 16-byte slot per id ever issued
    200'000,                     // override nodes
    8, sizeof(account),          // max chain depth, widest record
    "data.ckp">;                 // enables restart()

storage::field_storage<spec> table;
if (!table.ok()) return 1;
table.restart(8ull << 30);       // falls back to a full replay by itself

const auto id = table.create(account{ 500, now_ms(), "ada" });
table.update<&account::balance>(id, 450);      // writes 8 bytes, not 88
if (auto a = table.get<account>(id)) use(a->balance);

table.sync();                    // durability barrier - see §8 before choosing when
```

Paths can be given at run time, which is what a sandboxed process needs:

```cpp
storage::field_storage<spec> table(storage::storage_paths::under<spec>(app_dir));
```

Two things worth knowing before you build on it, both expanded in the spec:

- **`get<T>()` returns a copy, not a pointer.** The current record does not
  exist at any address - the base is where it was created and each override is
  wherever the log happened to be. Say `auto`, never `const T*`.
- **The barrier must be spaced by more than it costs.** A `sync()` placed at the
  device's own single-page latency spends all its time being the previous one.
  Size the interval against the bytes an operation dirties, per phase, not once
  per program.

## Replication

WAL shipping to N replicas, snapshot bootstrap, desync detection from both
ends, per-replica progress accounting. Engine-agnostic: both classes take the
table as `auto&` and the suite runs every scenario against both engines.

Full specification: **[`replication/REPLICATION.md`](replication/REPLICATION.md)**.

There is deliberately **no synchronous commit**. `create()` and `update()` stay
instant and infallible; "wait until my write reached a quorum" is a loop the
caller writes over the counting primitives, with its own timeout, at the call
site that cares.

# The UDP transport

Single-threaded per instance, built on `io_uring`. Every layer is built and
benchmarked in isolation first (levels 1-6), then unified into one class
(level 7). Guiding principle: batch everything, avoid per-packet syscall
overhead, and never trade away a security property for throughput without
saying so explicitly.

| Level | Concern | Key file |
|---|---|---|
| 1 | Raw `io_uring` UDP baseline: multishot `recvmsg` + provided buffer rings | `multishot_udp.hpp`, `uring_ring.hpp` |
| 2 | Noise_IK_25519_ChaChaPoly_SHA256 handshake (hardcoded state machine, not a generic pattern interpreter) | `noise_ik.hpp` |
| 3 | Message fragmentation/reassembly via a sliding-window bitmask | `packet_assembly.hpp` |
| 4 | Transport encryption tying the handshake and reassembly together (AEAD with the fragment header as associated data) | `transport_connection.hpp` |
| 5 | Anti-DoS: sliding-window replay protection + stateless cookie/load-gate under flood | `replay_window.hpp`, `anti_dos.hpp` |
| 6 | Optional per-message reliability: SACK + batched timer-wheel retransmit + RTT-free AIMD congestion window | `reliability.hpp`, `timer_wheel.hpp` |
| 7 | Unified `protocol::protocol_endpoint` - one class wiring all six together, queue-based (not callback-based) API | `protocol.hpp` |

Every module under `net/` is header-only; each `.hpp` is self-contained.

### Wire format (level 7)

One byte of type, then an 8-byte caller-assigned `conn_id`, then a type-specific body:

```
1 = handshake message1: type(1) | conn_id(8) | noise_msg1(with mac1) | mac2(16, zero if none yet)
2 = handshake message2: type(1) | conn_id(8) | noise_msg2
3 = data packet:        type(1) | conn_id(8) | <connection wire packet>
4 = cookie reply:       type(1) | conn_id(8) | cookie(16)
5 = SACK batch:         type(1) | conn_id(8) | count(1) | count * 14-byte entries
6 = keepalive:          type(1) | conn_id(8) | nonce(8) | AEAD tag(16), no payload
```

`conn_id` is caller-assigned and must be unique among an endpoint's live sessions - two peers using the same `conn_id` against the same endpoint will collide (one silently evicts the other's session). `level7_protocol_client` randomizes it by default; pass `--conn-id N` to pin one.

### API shape: two queues, not callbacks

`protocol_endpoint::handle_cqe()` only ever files results away. `poll_incoming()` drains everything that arrived since the last call in one batch - a `std::vector<event>` move, not a callback whose call stack is dictated by the CQE-draining loop. `send_message()` queues data and returns immediately; the actual encrypt+send happens in `tick()`, which is also where a reliable session's congestion window is enforced.

```cpp
protocol::protocol_endpoint<> endpoint(ring, fd, std::move(local_static), config);
endpoint.arm();
endpoint.connect(conn_id, remote_static_pubkey, addr, addr_len);

for (;;) {
    ring.submit_and_wait_timeout(1, 20ms); // not a plain wait - see uring_ring.hpp
    ring.drain_cqes([&](io_uring_cqe* cqe) { endpoint.handle_cqe(cqe); });
    for (auto& event : endpoint.poll_incoming()) {
        // handle handshake_established / handshake_failed / message_received / peer_unreachable however you like
    }
    endpoint.send_message(conn_id, some_payload, /*reliable=*/true);
    endpoint.tick(std::chrono::steady_clock::now());
}
```

Authorization/sessions/JWTs are deliberately **not** this protocol's job - that's application business logic. What the protocol does hand the application is a cryptographically-proven peer identity (`event::peer_static`, only ever populated once Noise_IK has verified the peer holds the matching private key) - what to do with that (allow, whitelist, rate-limit per key) is the caller's decision.

## Security design

- **Noise_IK** (level 2): the initiator's static key is AEAD-encrypted in message 1 (hidden from passive eavesdroppers); the responder's identity is never sent at all. A WireGuard-style `mac1` (HMAC over a hash of the responder's static key) filters out senders who don't even know the responder's public key, for the cost of one HMAC - before any DH is attempted.
- **AEAD-as-associated-data** (level 4): the fragment header (`msg_id`, `frag_index`, `frag_count`) is passed to the AEAD call as associated data, not encrypted. It needs integrity, not confidentiality - binding it as AD means any tamper to the header *or* the ciphertext fails the same authentication check, before `packet_assembly::Reassembler` (which trusts every field it's handed) ever sees it.
- **Replay window** (level 5): a sliding bitmap (RFC 6479/WireGuard style) rejects a byte-identical replay of an already-accepted nonce. `check()` (pre-decryption) never mutates state; `commit()` only runs after AEAD verification succeeds - otherwise a forged packet with a huge nonce could desync the window for free.
- **Stateless cookie / load gate** (level 5): under measured load, a responder replies to a handshake attempt with a cheap "here's your cookie" instead of spending a DH - a source-spoofing attacker never completes the round trip needed to make the responder do real work, without the responder keeping any per-source state.
- **Nonce/msg_id separation** (levels 4+6, QUIC-style): a naive design ties packet-identity (the AEAD nonce, replay-checked) to data-identity (the fragment's `msg_id`), which breaks the moment reliability needs to retransmit - a byte-identical retry reuses an already-committed nonce and gets replay-rejected forever, so a sender whose ack was lost can never learn its data arrived. The fix: every transmission attempt (including retries) gets a **fresh nonce** (`connection::encrypt_fragment`), while `msg_id` alone drives dedup/reassembly. A retransmit of an already-completed message is recognized by `reassembler::result::duplicate_of_completed`, which re-marks the slot dirty so a fresh SACK goes out - the receiver-side half of the fix that makes retrying and replay protection compatible at all.
- **AIMD congestion control without RTT measurement** (level 6): classic Reno-style AIMD doesn't need an RTT sample for the window logic itself. The two signals it uses are already free: an ACK arriving grows the window (slow start below `slow_start_threshold`, `+kCongestionAvoidanceStep` per round trip in congestion avoidance); a retransmit actually firing (the only loss signal available) halves it. A decrease is capped at one per cooldown window (`initial_timeout`) - a burst of loss spanning several consecutive retransmit ticks is one congestion event, not one per tick, which would otherwise cascade a single event into a much deeper collapse than one halving.
- **NAT keepalive** (level 7): UDP has no connection-reset signal, so an idle session's NAT/firewall mapping can silently expire (carrier-grade NAT in particular can time out well under a minute), breaking the session with no error surfaced to either side. `tick()` tracks how long it's been since a session last had anything to send; once that exceeds `protocol_endpoint<keepalive_interval_ms>`'s own compile-time interval (default 20000ms - a template parameter, like `connection`/`reassembler`'s window size, since every real deployment wants the same value), it sends a type=6 keepalive instead. It's a dedicated wire type, not a reuse of the data channel with an empty payload, specifically so it never touches `packet_assembly::reassembler` and can never surface as a `message_received` event - `handle_keepalive()` only calls `connection::decrypt_keepalive()` (AEAD-authenticated, replay-checked exactly like a data packet's nonce) and drops the result. A session that already sent real traffic (data, a SACK, a retransmit) this tick has its idle clock reset for free and never gets a redundant keepalive stacked on top.
- **Hanging-connection cleanup** (level 7): two distinct timeouts, both template parameters alongside `keepalive_interval_ms` for the same "every real deployment wants the same value" reason. `liveness_timeout_ms` (default 60000ms, ~3 missed keepalive cycles) tears down an established session that's gone quiet - `tick()` tracks `last_received_time` per session (updated only on *authenticated* data/keepalive, or on a SACK, so an unauthenticated packet can't fake liveness) and fires a `peer_unreachable` event carrying the peer's proven static key (not just the now-dead `conn_id`) once it's exceeded. `handshake_timeout_ms` (default 5000ms) is the separate, much shorter timeout for a `connect()` whose responder never answers at all - previously such an attempt sat in `pending_initiators` forever with no signal; now it fires `handshake_failed` like any other rejected handshake. A cookie-reply retry resets this clock (the responder proved it's there, just under load), so a slow-but-progressing retry isn't punished the same as true silence.

## Transport benchmarks

**Local (16-core desktop, loopback):**

| Level | Metric | Result |
|---|---|---|
| 1 - raw io_uring baseline | pps | ~383,000 |
| 2 - Noise_IK handshake | handshakes/s | ~2,300 (full), ~4,600 (one-sided) |
| 3 - fragment reassembly | pps | ~322,000 |
| 4 - full transport (handshake+AEAD+reassembly) | pps | ~310,000 |
| 5 - anti-DoS under flood | legit handshakes still complete 20/20 while dh_attempts/s collapses under a ~6,400 pps flood | |
| 6 - reliability under 0/15/30/50% simulated loss | 199-200/200 delivered, 0 given up | |
| 7 - unified protocol_endpoint, unreliable | pps | ~310,000 |
| 7 - unified protocol_endpoint, reliable | pps | ~290,000, `replay_rejected` stays 0 for the whole run |

**VPS (1 vCPU, 960MB RAM, real network path):** roughly a third of the local numbers (one core shared between client and server processes, plus real network latency instead of loopback) - same qualitative behavior, `replay_rejected=0` throughout, no crashes or collapses. CPU utilization stayed under 20% even at the VPS's peak throughput, meaning the congestion window's ramp-up rate (not CPU or the network) was the binding constraint at the tested durations.

## Running the level 7 demo

```
./build/level7_protocol_server <port> [load_threshold] [initial_cwnd] [initial_ssthresh]
./build/level7_protocol_client --server-pubkey <64 hex printed by the server> --host H --port P \
    [--message-size B] [--in-flight K] [--seconds S] [--reliable] [--conn-id N] \
    [--initial-cwnd N] [--initial-ssthresh N]
```

`--initial-cwnd`/`--initial-ssthresh` (client flags, or positional args 3/4 on the server) are an escape hatch for a link whose real capacity you already know from prior measurement - raising them skips most of the slow-start ramp. Guessing too high on a link of *unknown* capacity risks the same early congestion collapse this project hit and fixed during tuning; the defaults are the safe, conservative starting point.

# Building and testing

```sh
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)
ctest --test-dir build --output-on-failure
```

Under ASan/UBSan - tests only, do not benchmark through this build:

```sh
cmake -B build-asan -DENABLE_SANITIZERS=ON
cmake --build build-asan -j$(nproc)
ctest --test-dir build-asan --output-on-failure
```

`ctest` runs five cases: `unit_tests` (**197 doctest cases, 12,906
assertions**), `replication_tests` (**71 checks**, every applier scenario
against both engines, over real loopback endpoint pairs for the networked
half), `amalgam_current` (the single-header build is not stale), `amalgam_smoke`
(it compiles and works on its own) and `amalgam_smoke_builtins` (the same,
with `std::atomic_ref` forced off, which is the path Android takes).

Seven libFuzzer targets live in `tests/fuzz/` behind `-DENABLE_FUZZERS=ON`
(needs clang), covering the Noise handshake, packet assembly, SACK decoding,
transport decryption, storage recovery and WAL application.

**Dependencies** are for the transport, not the engine: `liburing` 2.4+ (needs
`io_uring_setup_buf_ring`), `libsodium` 1.0.19+ (needs the HKDF-SHA256
functions), CMake 3.20+, a C++23 compiler. The storage engine needs none of
them.

## Porting

```sh
cmake --build build --target platform_check && ./build/platform_check
```

Run that first on any platform that is not Linux. It exercises each shim in
`embedded/platform.hpp` against a real file and checks the property the engine
depends on - that space is genuinely reserved rather than sparse, that
preallocating twice is idempotent, that a page-aligned subrange flushes -
rather than that the calls returned zero.

### What is verified where

| | compiles | tests run |
|---|---|---|
| Linux x86-64 | yes | yes - `ctest`, Release and ASan/UBSan |
| Android x86-64, **16 KB pages** | yes | **yes** - the engine's 87 cases, and a replica of a host primary |
| Android arm64 | yes, NDK r27 clang | no device here; both CRC paths checked in the emitted code |
| macOS / iOS | **no** - no Darwin toolchain here | no |

`bench/replica_node.cpp` is the end-to-end one: the same binary is a primary
here and a replica on the phone, both on the epoll transport, and the replica
brought over 2,000 records with a matching checksum and offset. That is the
engine, replication and the transport working at once on hardware that is not
the development machine.

```sh
tools/android_test.sh          # needs an NDK and a device or emulator on adb
```

The Android run is the whole engine suite plus `platform_check` and the
single-header smoke test, on an image with **16 KB pages** - which is the
configuration that makes the page-size assumption a real bug rather than a
theoretical one. Four things had to be fixed to get there and not one of them
would have been found by reasoning:

- `crc32c` used SSE4.2 intrinsics, so nothing ARM compiled at all;
- `std::atomic_ref` does not exist in the NDK's libc++ (LLVM 19 added it, r27
  ships 18), so the engine falls back to `__atomic_*` builtins - a path `ctest`
  runs here via `STORAGE_FORCE_ATOMIC_BUILTINS`, because a branch that only
  executes on a phone is one nobody has watched work;
- `compact()` adopts the caller's scratch region as the engine's base, and the
  destructor unmapped it unconditionally - so passing a `std::vector`, which
  this repo's own tests do, meant `munmap()` on the heap. glibc tolerated it for
  months; bionic turned it into a SIGSEGV, which is the honest reaction;
- a test type named `user` is ambiguous against bionic's `struct user`.

Two of those were engine bugs that Linux was hiding.

**The Darwin paths are unverified**, and that is the honest gap in this release.
They were written against Apple's documented behaviour and reviewed, never
compiled and never run. Review already caught one bug a compiler would not have,
which is a fair warning about the rest; see
[`embedded/README.md`](embedded/README.md). Run `platform_check` first on a Mac
and expect to fix something.

# What is not here

- **No query language, planner or joins.** Secondary indexes live in user code
  over the observer; `bench/app_layer.hpp` is a worked example with unique
  constraints, foreign keys, triggers and staged transactions.
- **No MVCC and no concurrent writers.** Readers are safe in two narrow forms
  and no others: freely while no writer runs, and inside a commit via a
  seqlock. Everything else is a data race.
- **No cross-instance transactions.** Sharding is N instances with N sets of
  paths and nothing shared, which is also why their ids collide by design - an
  id is only meaningful together with the instance that issued it.
- **No failover or leader election.** Replication moves bytes and counts
  progress; promoting a replica is the caller's.
- **No authorization in the transport.** It proves peer identity and stops
  there.

`storage/cached_storage.hpp`, `storage/hybrid_storage.hpp`,
`storage/direct_gather.hpp` and `storage/uring_gather.hpp` are kept but **are
not part of the supported surface** - no tests, no specification, no
compatibility promise. They are the experiments whose measurements decided the
design, and deleting them would delete the evidence.
